# Implementation Plan

- [ ] 1. 基盤: 解放処理を常駐リーパーへ移す

- [x] 1.1 常駐リーパーを実装する
  - プロセスにつき 1 つだけ生成され、プロセス終了まで生存する実行主体を用意する
  - 解放要求（プールのクローンとスキーマ名）を受け取り、プールを閉じてからスキーマを削除する
  - 送信操作は呼び出し側をブロックせず、パニックもしない。`Drop` の内側から安全に呼べる
  - 解放の成否でテストを失敗させない。失敗はログに留める
  - 完了状態: 解放要求を送ったあと呼び出し側のランタイムが破棄されても、プールが閉じられ
    スキーマが削除されることを検証する単体テストが緑になる
  - _Requirements: 2.1, 2.3_
  - _Boundary: HarnessReaper_

- [x] 1.2 TestApp の解放をリーパー委譲に置き換える
  - `Drop` の実装を、スキーマ削除のデタッチからリーパーへの送信に置き換える
  - 明示的な後始末の経路は変更しない（既存の呼び出し側を書き換えない）
  - 同一プールに対して明示経路とリーパー経路の両方が走っても破綻しないことを確認する
  - 完了状態: 後始末を呼ばずに多数のインスタンスを生成・破棄しても、保持接続数が
    生存インスタンス数に比例する範囲に留まることを検証する統合テストが緑になる
  - _Requirements: 2.1, 2.2, 2.3, 2.4, 2.5_
  - _Depends: 1.1_

- [ ] 2. 孤立スキーマの回収

- [x] 2.1 (P) 回収可否の判定を実装する
  - スキーマ名に埋まった生成時刻をパースし、閾値より古いものだけを回収対象と判定する
  - パースできない名前、閾値より新しい名前は対象外とする（実行中の他プロセスを巻き込まない）
  - 完了状態: 古い名前・新しい名前・パース不能な名前それぞれに対する判定を検証する
    単体テストが緑になる
  - _Requirements: 3.2_
  - _Boundary: OrphanSchemaSweeper_

- [x] 2.2 起動時スイープを実装し初回フィクスチャ生成に接続する
  - プロセス内で最初にフィクスチャが生成されたときに 1 度だけ実行する
  - 回収失敗はログに留め、テスト実行を止めない
  - 完了状態: 古い孤立スキーマを人工的に作った状態でテストを実行すると回収され、
    新しいスキーマは残ることを検証する統合テストが緑になる。事前のスキーマ掃除なしで
    テストが実行できる
  - _Requirements: 1.2, 3.1, 3.3, 3.4_
  - _Depends: 2.1_

- [ ] 3. 軽量 DB フィクスチャへの移行

## Implementation Notes

- 1.1: `src/test_harness.rs` の `mod reaper;` に付けた `#[allow(dead_code)]` は 1.1/1.2 分割による
  過渡的なもの。`src/lib.rs` が `pub mod test_harness` を無ゲートで公開しているため、production
  caller（`Drop for TestApp`）が来る 1.2 まで全項目が未使用警告になる。**1.2 でこの属性を外すこと。**
- 3.1: `TestDb.runtime.keys` は `RuntimeContext::deterministic` の `FixedSigningKeyProvider` の
  まま。design の TestDb Invariant が clock / id / RNG のみを列挙し keys を意図的に外していること、
  および「署名鍵生成を行わない」が根拠。`DbSigningKeyProvider` は `KeyCache` と `ActorModule` を
  要求するので、そもそも TestDb が禁じられているモジュール構築が必要になる。
- 3.1: schema+pool+migrate の並びは `establish_isolated_db()` に集約済み。`spawn_test_app` と
  `spawn_test_db` の両方がこれを通る。新しいフィクスチャを足すときもここを通すこと。
- **未解決の欠陥（要 follow-up、本 spec の要件 3.1 / 1.2 に関わる）**: `src/federation/test_harness.rs`
  の連合ペアハーネスは schema+pool+migrate の 3 つ目の複製を持ち、(a) 起動時スイープを呼ばず、
  (b) スキーマ接頭辞が `kawasemi_federation_pair_` で `HARNESS_SCHEMA_PREFIX` に一致しない。
  結果として**異常終了で孤立した連合ペアのスキーマはどのスイープでも回収できない**。正常終了時は
  `TestApp` の `Drop` がリーパーへ委譲するので実害は出ていない（実測でも残存 0）。タスク 6.1 の
  一括実行前に判断が要る。
- 2.2: 回収閾値は 2 時間（フルスイート 891 秒の約 8 倍）。誤射しても被害は「そのプロセスの以後の
  クエリが `relation does not exist` で大きな音を立てて落ちる」であって静かな破壊ではないが、
  過剰回収は不可逆なので長めに倒してある。
- 2.2: スキーマ一覧に `LIKE 'kawasemi_test_harness_%'` を使わないこと。**`_` は LIKE の
  ワイルドカード**なので、このパターンは見た目より広く一致する。全件列挙して Rust 側の
  `is_reclaimable` で絞る。
- 2.2 申し送り（4.2 の完了条件に含めること）: `pub mod sweep` と `sweep_orphans_now` /
  `startup_sweeps_performed` は統合テストから駆動するために design のインターフェースを超えて
  公開している。`test-harness` feature ゲートの内側に確実に入れること（Requirement 5.2）。
- 2.1: 回収述語の失敗様式は非対称。過剰保持は安いが過剰回収は実行中の別プロセスの DB 状態を
  破壊する。パース不能・未来時刻・桁溢れはすべて「保持」に倒す。特に `duration_since` を
  `Result` で受けること（`Duration` の減算 underflow は「巨大な age＝回収対象」に化ける）。
- 2.1: `unique_schema_name` は `sweep::HARNESS_SCHEMA_PREFIX` を参照する形にした（命名規約と
  判定側の結合を構造化）。`tests/harness_release_it.rs` は統合バイナリで `pub(crate)` が
  見えないため独自の複製を持つが、同ファイルが実 DB の `current_schema()` に対して
  `starts_with(HARNESS_SCHEMA_PREFIX)` を主張しているのでドリフトは検知される。
- 2.2 でやること: `sweep.rs` の `is_reclaimable` に付いた `#[allow(dead_code)]` を外し、
  閾値の実値を決める（フルスイート約 891 秒より十分に大きく取る）。
- 1.2: 真因の内訳が判明した。統合テストのプロセスでは外側ランタイムが生き残るため、旧 `Drop` の
  デタッチ経路でも**スキーマ自体は落ちていた**。一度も起きていなかったのは `pool.close()` で、
  破棄ごとに約 2 接続ずつ積み上がっていた（40 個中 10 個目で baseline+22）。
- 1.2: 共有テスト DB を測るテストは**テスト間分離を自前で持つこと**。`information_schema` を
  サーバ全体で舐めると兄弟テストの生存スキーマを自分の残骸と誤検出して flaky になる（実際に
  1 回目 FAIL / 2 回目 PASS を踏んだ）。自プールへの `current_schema()` で自分のスキーマを特定し、
  `schema_name = ANY($1)` で自分のぶんだけを見る。加えてバイナリ内は静的 `tokio::sync::Mutex`
  （poison を持たないのでパニックするテストが波及しない）で直列化する。
- 1.2 申し送り: `pg_stat_activity` による接続数の観測は「同時に別のテストバイナリが同じ DB を
  触らない」ことに依存する。`cargo test` はテストターゲットを逐次実行するので現状は成立するが、
  `cargo nextest` 等のプロセス並列実行器を導入すると崩れる。タスク 6.x で実行形態を変える際は
  この前提を確認すること。
- 1.1: リーパーは 1 スレッド + current-thread ランタイムで逐次処理し、`drop_schema` ごとに
  短命 admin プールを開閉する（同時 admin 接続は最大 1）。fan-out させると本 spec が解消しようと
  している接続枯渇を悪化させるため、この逐次性は意図的。
