## 3. 隔離スキーマの残留（要件 5.4 / 5.5 のベースライン）

各試行の直後に残存スキーマを列挙した結果:

```
trial 1 後: kawasemi_test_harness_1786702184893703666_0
trial 2 後: kawasemi_test_harness_1786702184893703666_0
            kawasemi_test_harness_1786702817788330979_2
trial 3 後: kawasemi_test_harness_1786702184893703666_0
            kawasemi_test_harness_1786702817788330979_2
            kawasemi_test_harness_1786703441951596336_1
```

**フルスイート 1 回につきスキーマが 1 つ残り、後続の試行でも回収されない。**
これは**移設前から存在する既存のふるまいであり、本 spec が作り出したものではない**。

理由は**2 段階**あり、どちらもハーネスの設計どおりである。両方を挙げないと説明にならない。

1. **なぜ残るか** — `src/test_harness/reaper.rs`。リーパーはプロセス終了時のベストエフォートであり、
   終了時点でキューに残っていた回収要求は失われ、次回のスイープに委ねられる。
   したがって 1 回の実行につき「最後に取りこぼした 1 個」が残るのは想定内の挙動
2. **なぜ後続の実行で回収されないか** — `src/test_harness/sweep.rs` の `RECLAIM_THRESHOLD` が
   **2 時間**であり、スイープは「埋め込まれた時刻が閾値以上過去にある」スキーマしか落とさない。
   判断に迷うものはすべて「残す」側へ倒し、並行実行中の別プロセスのスキーマを誤って落とさないことを
   優先している。試行間隔は約 10 分なので閾値に達しておらず、残るのが正しい。2 時間後の実行が回収する

残ったスキーマ名に埋め込まれたナノ秒時刻を復号すると 19:09:44 / 19:20:17 / 19:30:41 で、
いずれも**当該試行の終了 70〜80 秒前**という再現的な位置にある。

**この「終了間際」という観察は、後から誤読だったと判明した**（§7.3）。末尾インデックスは
生成順のカウンタであって解放順ではなく、決定要因はテストの**終了順**だった。

> **⚠ 以下の暫定提案は撤回した。§7 を見ること。**
>
> 当初この節は「要件 5.5 の判定を絶対値ゼロではなく非悪化へ読み替える」ことを提案し、
> その根拠として**現行ハーネスでは絶対値ゼロは原理的に達成できない**と述べていた。
> **この前提は誤りだった。** タスク 8.3 の真因調査で判明したとおり、リーパーの取りこぼしが起きるのは
> **`cleanup()` を呼ばずに `Drop` に解放を委ねた場合だけ**である。`cleanup().await` は
> プールを閉じスキーマを DROP し終えてから返り、`schema` を `Option` から take するため
> `Drop` はリーパーに何も渡さない（`src/test_harness.rs:602-631, 641-667`）。
> **既存 `tests/*_it.rs` 92 本はこの規約を守っており残留ゼロだった。**
>
> したがって要件 5.5 の読み替えは不要であり、人間承認を求めていた論点も消滅した。
> 移設前のベースライン 1 件は「原理的な限界」ではなく、
> `cleanup()` を呼んでいなかった 1 ファイル（`tests/social_graph_visibility_query_it.rs`）に由来する
> **既存の規約違反**だった。

## 4. 移設が実行時間に効く経路（8.3 の切り分け用）

コンパイルが 0.2 秒未満である以上、増分の出どころは以下に限られる。**いずれも仮説であって
計測に基づく順位づけではない。** 8.3 で 1.2 倍を超えた場合はこの順に疑うのが妥当と考えるが、
断定はしない。

1. **プロセス起動オーバーヘッドと逐次化** — テストバイナリは逐次実行されるため、19 本分の
   起動・終了・接続確立が直列に加算される
2. **バイナリ内並列度の低下** — 1 本に 24 テストあったものが独立バイナリに分かれると、
   バイナリ内 16 スレッドの並列枠を使い切れず、全体としては直列化が進む方向に働く。
   最大 24 テストのファイルが分離される以上、これは確実に起きる
3. **バイナリごとのスイープ** — `sweep_orphans` は「最初のフィクスチャが配られる前」に
   **プロセスにつき 1 回**走る（`sweep.rs`。`OnceCell` による）。バイナリが 19 本増えれば
   スイープも 19 回増える。ただし `sweep.rs` 自身が 1 パスのコストを「239 スキーマの滞留でも
   1 秒未満」と述べており、**実費は小さい可能性が高い**。1・2 を先に疑うこと

いずれも「移設先ファイルの粒度をドメイン単位へ統合してバイナリ数を減らす」（要件 5.3）で緩和できる。
逆に言えば、**テスト自体の実行時間は変わらない**（同じ `spawn_test_app` を同じ回数呼ぶ）。

## 5. 再現手順

after の計測はこのスクリプトをそのまま再実行すること（`cargo build --tests` によるウォームアップを含む）。

```bash
#!/usr/bin/env bash
set -u
cd /path/to/kawasemi
OUT=<出力ディレクトリ>
mkdir -p "$OUT"

{
  echo "date: $(date -Iseconds)"
  echo "git HEAD: $(git rev-parse --short HEAD)"
  echo "nproc: $(nproc)"
  echo "cargo: $(cargo --version)"
  echo "rustc: $(rustc --version)"
} > "$OUT/conditions.txt"

# ウォームアップ（この時間は計測に含めない）
/usr/bin/time -f "warm_build_wall=%e" -o "$OUT/warm_build.txt" cargo build --tests > "$OUT/warm_build.log" 2>&1

for i in 1 2 3; do
  /usr/bin/time -f "%e" -o "$OUT/trial_$i.time" cargo test > "$OUT/trial_$i.log" 2>&1
  echo "rc=$?" >> "$OUT/trial_$i.time"
  psql "postgres://kawasemi_test:kawasemi_test_pw@127.0.0.1:5432/kawasemi_test" -tAc \
    "select schema_name from information_schema.schemata where schema_name like 'kawasemi\_%'" \
    > "$OUT/schemas_after_trial_$i.txt" 2>&1
done
```

通過本数の集計:

```bash
grep -oP '^test result: ok\. \K[0-9]+' "$OUT/trial_3.log" | paste -sd+ | bc   # passed
grep -oP '(?<=; )[0-9]+(?= failed)'    "$OUT/trial_3.log" | paste -sd+ | bc   # failed
grep -c '^\s*Running' "$OUT/trial_3.log"                                     # テストバイナリ数
```

**注意**: フルスイートの出力を `tail` で切らないこと。失敗理由が失われる（HANDOFF §5）。

### 実行時間についての結論

**移設は実行時間をほとんど動かさなかった。** 定常状態の比較（移設前 622.67 / 634.80 vs 移設後 640.89 / 636.22）で
差は 3% 以内であり、中央値の比 1.01 は判定基準 1.20 に対して大きな余裕がある。**要件 5.3 の是正措置（移設先
ファイルの粒度統合）は不要。**

§4 で立てた 3 つの仮説は、**合計としては**支配的でなかった。テストバイナリが 89 → 108 と 19 本増えても、
全体の増分は測定可能な規模に達していない。実行時間の大半が DB 律速であり、バイナリ境界のオーバーヘッドは
その中に埋もれる規模だったと解釈できる。

**ただしこの計測が言えるのはそこまでである。** 試行 1（883.78）と試行 3（636.22）の開きが示すとおり
本計測の解像限界は数十秒規模であり、**3 仮説の順位づけも、互いに相殺していないことの否定も、
このデータからは言えない**。言えるのは「3 つを合わせた正味の増分がノイズに埋もれる程度だった」ことだけ。
なお定常試行同士（622.67 / 634.80 → 640.89 / 636.22）を比べると +1.6% の一貫したわずかな増加はある。

### テスト総数の保存（要件 2.6）

**passed が移設前後で 2286 と完全に一致した。** failed 0 / ignored 5 も同一。
`inventory.md` §5 が移設着手前に予測した「移設後 src 1589 / tests 697 / 合計 2286 不変」とも一致する。
移設によるテスト関数の増減はゼロであり、要件 2.6 の「差分が説明可能であること」は
**そもそも差分が存在しない**という形で満たされる。

## 7. 隔離スキーマの残留 — 移設で悪化し、真因を除去して 0 にした（要件 5.4 / 5.5）

### 7.1 観測された退行

計測開始時点の残存は 6 件。各試行後の残存総数と、**集合差で求めた新規生成数**:

| | 移設前（新規生成） | 移設後（総数） | 移設後（**新規生成**） |
|---|---|---|---|
| 試行 1 後 | +1 | 10 | **+4** |
| 試行 2 後 | +1 | 14 | **+4** |
| 試行 3 後 | +1 | 17 | **+4** |
| 1 実行あたり | **1（一定）** | — | **4（一定）** |

**総数の差分（+4 / +4 / +3）で読んではならない。** 試行 3 の +3 は正味の値で、
新規に 4 件生成される一方、既存 1 件（`kawasemi_test_harness_1786710779740001397_16`）が
2 時間閾値を越えて起動時スイープに回収された相殺による。集合差では**新規生成は 3 試行とも 4 件で一定**。

```
comm -13 <(sort schemas_after_trial_2.txt) <(sort schemas_after_trial_3.txt) | wc -l   # 新規 4
comm -23 <(sort schemas_after_trial_2.txt) <(sort schemas_after_trial_3.txt)           # 回収 1
```

### 7.2 犯人バイナリの特定

スキーマ名に埋め込まれたナノ秒時刻を復号し、試行ログの累積実行時間と突き合わせた結果:

| 残留時刻 | バイナリ | 由来 |
|---|---|---|
| 429s | `tests/notifications_service_it.rs` | **本 spec タスク 4.2 で新設** |
| 500s | `tests/search_service_it.rs` | **本 spec タスク 3.1 で新設** |
| 533s | `tests/social_graph_follow_request_service_it.rs` | **本 spec タスク 5.2 で新設** |
| 546s | `tests/social_graph_visibility_query_it.rs` | 既存（移設前のベースライン 1 件の出所） |

4 件中 3 件が本 spec の新設ファイル。「バイナリが増えたから比例して増えた」ではない。

### 7.3 真因

`TestApp` / `TestDb` の `Drop`（`src/test_harness.rs:641-667`）は解放を自分では行わず、
`HarnessReaper` へ**非同期に委譲する**。リーパーのキューはプロセス終了時に無条件で破棄される
（`src/test_harness/reaper.rs:112-113`）。libtest は最後のテストが返った直後に exit するため、
**そのプロセスで最後に submit された 1 件だけは完了する時間が構造的にゼロ**になる。
したがって規約違反のバイナリは 1 個ずつ、確実に漏らす。

`--test-threads=1` で必ず最終インデックスが漏れ、並列時は揺れる。決定要因が生成順ではなく
**テスト終了順**であることの決定的証拠である。

**そして本当の差分はバイナリ数ではなく `cleanup()` 規約の遵守率だった。**
`cleanup().await`（`src/test_harness.rs:602-631`）はプールを閉じスキーマを DROP し終えてから返り、
`schema` を `Option` から take するので `Drop` はリーパーに何も渡さない。
既存 `tests/*.rs` のうちフィクスチャを使う 92 本はこの規約を守っており残留ゼロだった。
移設元の `src/**/tests.rs` は規約を守っておらず、**1779 テストが同居する単一プロセスに守られて
顕在化していなかっただけ**。プロセス分割がそれを露出させた。

### 7.4 施した修正と実測

4 ファイルの全テストに `cleanup().await` を追加した（**純粋な追加 +72 / −0**。
アサーション・入力・期待値・制御フローは 1 文字も変えていない）。

| ファイル | 追加 | 既定スレッド | `--test-threads=1` |
|---|---|---|---|
| `tests/search_service_it.rs` | +22 | 1 → **0** | 1 → **0** |
| `tests/social_graph_follow_request_service_it.rs` | +16 | 1 → **0** | 1 → **0** |
| `tests/notifications_service_it.rs` | +28 | 1 → **0** | 1 → **0** |
| `tests/social_graph_visibility_query_it.rs` | +6 | 1 → **0** | 1 → **0** |

**単一スレッドでも 0 になったことが、頻度低減ではなく真因除去であることを示す。**
単一スレッドでは最後に終わるフィクスチャが決定的になるため、偶然の green を排除できる。

4 ファイル目は本 spec より前から存在し design.md「Boundary Commitments」が Out of Boundary と
定めているが、**ユーザーの明示的承認に基づく境界の拡張**として修正した。加えたのは teardown のみで
検証内容は不変であり、境界が守ろうとしている「既存の検証内容を変えない」という趣旨は保たれている。

### 7.5 要件の判定

- **要件 5.4（完走・上限超過なし）: 満たされている。** 移設後 3 試行とも `rc=0` で完走し、
  同時に存在するスキーマ数が DB の上限に当たった形跡はない
- **要件 5.5: タスク 8.4 のフルスイート実測で判定する。** 上記は 4 / 108 バイナリの実測にすぎず、
  スイート全体が 0 であることの証明にはならない。静的走査では `tests/` `src/` とも
  「生成数 > `cleanup()` 数」のファイルは 1 つも残っていないが、**達成の宣言は 8.4 の実測を根拠とする**

### 7.6 残る構造的リスク（HANDOFF 必須）

**真因そのもの（リーパーのキューがプロセス終了時に破棄される）は未修正である。**
`reaper.rs` は先行 spec `test-infrastructure` の所有物で本 spec の Out of Boundary にあたる。
今後 `cleanup()` を呼ばないテストが追加されれば、同じ残留が再発する。

**これを自動で検出する仕組みはリポジトリに存在しない。** CI（`.github/`）なし、該当する lint なし、
`tests/harness_release_it.rs` はハーネス自己検証だが `wait_until_reclaimed` でプロセス内待機するため
**プロセス終了時の取りこぼしという当のふるまいを検出できない**。

さらに steering `.kiro/steering/structure.md:81` は
「**呼ばなくてもリークしない** — `Drop` がプールとスキーマ名を常駐リーパーへ渡す」と記しており、
**プロセス終了時については不正確で、規約の記述自体が再発を誘発する向きになっている**。
