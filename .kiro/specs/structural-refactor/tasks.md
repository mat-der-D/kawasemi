# Implementation Plan

段階の順序は design.md「Migration Strategy」に従う。**各段階（メジャータスク）の完了時点でフルスイートがグリーンであること**が共通の完了条件（Requirement 1.6）。テスト期待値を変更した場合は、それが仕様変更ではなく「テスト側が誤っていた」ことの修正である根拠を実装記録に残す（Requirement 1.4）。

---

- [x] 1. 失敗理由の識別をエラーメッセージ文字列から型へ移す

- [x] 1.1 横断エラー型にドメイン識別子を導入する
  - 横断エラー型に「どのドメイン条件で失敗したか」を表す省略可能な識別子を追加する。バリアントは重複投票の 1 種類のみとし、将来のための先回りバリアントは作らない
  - 識別子を設定できる 4xx 用コンストラクタを追加する。既存の 4xx / 5xx コンストラクタはシグネチャを変えず、識別子は未設定で埋める
  - 識別子はレスポンスボディにもログにも一切出さない。既定のボディレンダラーと Mastodon 互換ボディレンダラーのいずれも識別子を読まない
  - 完了状態：識別子を設定したエラーと設定していないエラーが、同一のステータスコード・同一のレスポンスボディを返すことを単体テストが示す
  - _Requirements: 1.1, 2.3, 2.4, 2.6_
  - _Boundary: AppError_

- [x] 1.2 重複投票の判定を型に切り替える
  - 投票記録における「既に投票済み」の拒否にのみ識別子を付ける。期限切れ・選択肢範囲外・単一/複数選択違反の 3 つの拒否は識別子を付けない
  - 拒否時のメッセージ文言とステータスコードは現状のまま一字も変えない
  - 受信 Activity ハンドラの重複投票分岐を、メッセージ文字列の比較から識別子の比較に置き換える。ステータスコードの比較は冗長になるため削除する
  - 完了状態：投票記録が返す 4 種類の拒否のうち重複投票だけが識別子を持つことを単体テストが示し、受信ハンドラが重複投票のみをべき等（処理済み）として扱い他の 3 つはエラーとして伝播することを既存テストが示す
  - _Requirements: 1.6, 2.1, 2.2, 2.5, 2.6_
  - _Boundary: PollRepository, InboundActivityHandler_

- [x] 2. エンドポイント横断の定型処理を横断層に集約する

- [x] 2.1 (P) クエリパラメータ解釈の単一実装を用意する
  - 件数上限パラメータの解釈（省略時・有効な 10 進数・非数値）と、緩い真偽値パラメータの解釈（真/偽の複数表記と、それ以外の拒否）を横断層に置く
  - 既存の private 実装からバイト単位で挙動を写す。「改善」しない
  - 移設元に紐づいていた単体テストを横断層側へ移す
  - 完了状態：横断層の単体テストが、省略時・有効値・非数値・真偽値の各表記について移設前と同一のステータスコードとメッセージを返すことを示す
  - _Requirements: 3.1, 3.4_
  - _Boundary: api::query_

- [x] 2.2 (P) 時刻整形の単一実装を用意する
  - エンティティの時刻フィールドを出力するための RFC3339 整形を横断層に置く
  - 4 箇所の private 実装が同一であることを確認した上で写す
  - 完了状態：横断層の単体テストが、移設前の各実装と同一の文字列を返すことを示す
  - _Requirements: 3.3_
  - _Boundary: api::time_

- [x] 2.3 (P) データストア障害のエラー変換の単一実装を用意する
  - データストアのエラーを横断エラー型のサーバーエラーへ変換する処理を横断層に置く
  - 同名の 11 実装が同一であることを確認して写す。名前の異なる残り 15 実装は、返すエラーの形（ステータス・公開メッセージ）が同一であることを個別に確認し、**同一と確認できたものだけ**を対象にする。異なるものは移設せず、その旨を実装記録に残す
  - 完了状態：横断層の単体テストが、変換後のステータスコードと公開メッセージが移設前と一致することを示し、移設対象外とした実装の一覧とその理由が記録されている
  - _Requirements: 3.5_
  - _Boundary: api::db_

- [x] 2.4 (P) 自インスタンスのオリジン解決の単一実装を用意する
  - リクエスト文脈を持たない場所（Activity 構築、通知やハッシュタグのシリアライズ）から自インスタンスの正規オリジンを組み立てる処理を横断層に置く
  - 完了状態：横断層の単体テストが、移設前の呼び出しと同一のスキームとホストを持つオリジンを返すことを示す
  - _Requirements: 3.6_
  - _Boundary: api::origin_

- [x] 2.5 エンドポイントとシリアライザを横断層の実装に移行する
  - 件数上限・真偽値・時刻整形の private 実装をすべて削除し、横断層の実装を呼ぶ。対象はアカウント／ソーシャルグラフ／タイムライン／通知／投稿／検索の各エンドポイントと、アカウント／投稿／通知の各シリアライザ
  - 緩い真偽値の解釈は分析レポートが 2 箇所としているが実測は 3 箇所（検索が数え落とされている）。3 箇所すべてを対象にする
  - 移設元の private 実装に紐づく既存テストは削除せず、横断層側へ移すか呼び出し経由で残す
  - ページネーション可能な全 7 箇所が横断層のリンクヘッダー組み立てを経由していること（独自組み立てが残っていないこと）を確認する。既に一元化されている想定であり、逸脱が見つかった場合のみ修正する
  - 完了状態：対象モジュールに件数上限・真偽値・時刻整形の private 実装が 1 つも残っておらず、リンクヘッダーの独自組み立ても存在せず、各エンドポイントの既存テストがグリーン
  - _Requirements: 1.1, 1.6, 3.1, 3.2, 3.3, 3.4, 3.7_
  - _Depends: 2.1, 2.2_

- [x] 2.6 エラー変換とオリジン解決を横断層の実装に移行する
  - 2.3 で同一と確認したデータストアエラー変換の private 実装を削除し、横断層の実装を呼ぶ
  - 自オリジン解決の 5 箇所（通知サービス／検索ハイドレータ／タグシリアライザ／アカウント投稿プロバイダ／フォローリクエストサービス）を横断層の実装に置き換える
  - 完了状態：移設対象としたエラー変換の private 実装が残っておらず、5 箇所の自オリジン解決がすべて横断層経由になっており、既存テストがグリーン
  - _Requirements: 1.1, 1.6, 3.5, 3.6, 3.7_
  - _Depends: 2.3, 2.4_

- [x] 3. Status レンダリンググルーを単一実装に集約する（振る舞い完全不変）

- [x] 3.1 レンダリング組み立ての単一実装と投票解決ポートを用意する
  - 解決済みの材料から Status のレンダリング入力を組み立てるコンポーネントを新設する。責務は「材料から組み立てる」ことに限り、ブースト先の解決と可視性判定は含めない
  - 経路ごとの差異を 2 つの注入点に押し出す：ミュート判定の材料（省略時はミュート無しとして扱う）と、投票の解決経路
  - 投票解決は差し替え可能なポートとして定義する。ジェネリックではなくボックス化した非同期トレイトにする（投稿エンドポイントの状態型が既に 6 個のジェネリック引数を抱えているため）
  - N 件版を主とし、1 件版は長さ 1 の呼び出しとして委譲する。この段階では内部は逐次処理のままでよい（バッチ化は次段階）
  - 完了状態：新コンポーネントの単体テストが、ミュート材料の有無で `muted` の出力が切り替わること、投票解決ポートの実装差で投票行が無い場合の挙動（エラー／省略）が切り替わることを示す
  - _Requirements: 4.2, 4.3, 4.4, 4.5, 4.6_
  - _Boundary: StatusRenderAssembler, PollResolver_

- [x] 3.2 投稿エンドポイントを単一実装に切り替える
  - 投稿エンドポイントの組み立てメソッド群を削除し、新コンポーネントへの委譲に置き換える。ブースト先の解決と可視性判定は投稿エンドポイント側に残す
  - 投票解決ポートは投票サービス経由の実装を供給する（可視性チェックを含み、行が無い／見えない場合はエラー）。5 経路のうちこれだけが解決経路そのものが異なるため最初に扱い、ポートの契約が妥当かを検証する
  - 完了状態：投稿エンドポイントに組み立てグルーが残っておらず、その既存テストと golden 契約テストがグリーン
  - _Requirements: 1.1, 1.6, 4.1, 4.3_
  - _Boundary: StatusesEndpoints_

- [x] 3.3 (P) アカウント別投稿一覧を単一実装に切り替える
  - 組み立てメソッド群を削除し新コンポーネントへ委譲する。投票解決ポートは「行必須・このモジュール固有の未検出エラー」の実装を供給する
  - 完了状態：当該モジュールに組み立てグルーが残っておらず、既存テストがグリーン

  - _Depends: 3.2_

- [x] 3.4 (P) 通知サービスを単一実装に切り替える
  - 組み立てメソッド群を削除し新コンポーネントへ委譲する。投票解決ポートは「行必須・このモジュール固有の未検出エラー」の実装を供給する
  - 閲覧者を非省略型で受けていた箇所は、省略可能型に設定済みの値を渡す形にする。挙動は同一
  - 完了状態：当該モジュールに組み立てグルーが残っておらず、通知の既存テストと golden 契約テストがグリーン

  - _Depends: 3.2_

- [x] 3.5 (P) タイムラインハイドレータを単一実装に切り替える
  - 組み立てメソッド群を削除し新コンポーネントへ委譲する。**5 経路で唯一ミュート材料を注入する経路**であり、フィルタ文脈のミュート集合を渡す
  - 現在時刻はフィルタ文脈由来の値をそのまま渡す（他 4 経路はランタイムのクロック由来）
  - 投票解決ポートは「行任意・行が無ければ省略」の実装を供給する
  - 完了状態：当該モジュールに組み立てグルーが残っておらず、ミュート済みアカウントの投稿がタイムライン経由でのみ `muted` を真として返すことを既存またはこの段階で追加したテストが示す

  - _Depends: 3.2_

- [x] 3.6 (P) 検索ハイドレータを単一実装に切り替える
  - 組み立てメソッド群を削除し新コンポーネントへ委譲する。投票解決ポートは「行任意・行が無ければ省略」の実装を供給する
  - このモジュールのドキュメントに残っている「4 番目の複製、共有ヘルパーを切り出す潮時」という CONCERN を削除する（本段階で解消されるため）
  - 完了状態：当該モジュールに組み立てグルーと該当 CONCERN が残っておらず、検索の既存テストがグリーン

- [x] 3.7 5 経路の表現一致を検証する統合テストを追加する

  - ミュート済みアカウントの投稿について、タイムライン経由では `muted` が真、他 4 経路では偽であることを検証する
  - 完了状態：上記 2 つの検証が通り、いずれかの経路だけを変更すると落ちる状態になっている

  - _Depends: 3.3, 3.4, 3.5, 3.6_

- [x] 4. 一覧取得のクエリ数を件数から切り離す

- [x] 4.1 (P) 投稿とメディアの一括取得を追加する
  - 複数の投稿 id からメディア id の対応表を一度に引く関数と、複数のメディア id からメディア実体の対応表を一度に引く関数を追加する
  - 既存の単数版は削除しない（他に呼び出し元がある）。複数版は単数版と同じ絞り込み条件・同じ並び順を使う
  - 空のスライスを渡した場合はクエリを発行せず空を返す
  - 完了状態：「単数版を N 回呼んだ結果と複数版を 1 回呼んだ結果が一致する」ことを検証する単体テストが通る
  - _Requirements: 5.1, 5.4_
  - _Boundary: StatusRepository, MediaRepository_

- [x] 4.2 (P) タグの一括取得を追加する
  - 複数の投稿 id からタグの対応表を一度に引く関数を追加する。既存の単数版は残す
  - 完了状態：「単数版 N 回 == 複数版 1 回」の単体テストが通り、空スライスでクエリを発行しない
  - _Requirements: 5.1_
  - _Boundary: TagRepository_

- [x] 4.3 (P) インタラクション状態の一括取得を追加する
  - 閲覧者と複数の投稿 id から、お気に入り済み／ブックマーク済み／ピン留め済み／ブースト済みの投稿 id 集合をそれぞれ一度に引く 4 関数を追加する
  - 完了状態：4 関数それぞれについて「個別存在チェックを N 回した結果と一括取得 1 回の結果が一致する」単体テストが通る
  - _Requirements: 5.1, 5.5_
  - _Boundary: InteractionRepository_

- [x] 4.4 (P) 投票の一括取得を追加する
  - 複数の投票 id から投票実体の対応表と集計結果の対応表をそれぞれ一度に引く関数を追加する。集計は閲覧者の投票済み判定を含む
  - 完了状態：「単数版 N 回 == 複数版 1 回」の単体テストが通り、閲覧者の投票済み判定が単数版と一致する
  - _Requirements: 5.1_
  - _Boundary: PollRepository_

- [x] 4.5 組み立ての N 件経路を一括取得とメモ化に切り替える
  - N 件版の組み立てを、対象となる全投稿（ブースト先を含む）の id・著者 id・投票 id を先にまとめてから、一括取得を呼ぶ形に変える
  - 絵文字は全投稿の本文と投票選択肢のタイトルから短縮コードを集めて 1 回で解決する
  - アカウント解決は 1 回の組み立て呼び出し内で著者ごとにメモ化する。**呼び出しをまたぐキャッシュは持たない**（ステイルなデータを返す新しい失敗モードを作らないため）
  - 一括取得の結果に含まれない id は現行の各経路の規約どおり縮退させる（メディアは黙って省く、投票は解決ポートの実装が決める）
  - 出力の並び順は入力の順を維持する
  - **1 件ずつ `assemble_one` をループしている 3 つの一覧経路（アカウント別投稿一覧・検索・通知）を、
    ページ分をまとめて `assemble_many` を 1 回呼ぶ形に変える。** ブースト先の解決と可視性の再判定は
    ループの外へ持ち上げる（各経路の判定規約そのものは変えない）。これをやらないと当該 3 経路は
    件数比例のまま残り、Requirement 5.1 が未達になり、著者メモ化の項目も一度も効かない
  - 完了状態：5 経路すべての既存テストと golden 契約テストがグリーンで、一覧レスポンスの JSON と並び順がバッチ化前と一致する
  - _Requirements: 1.1, 1.6, 5.1, 5.2, 5.3, 5.4, 5.5, 5.6, 5.7_
  - _Depends: 4.1, 4.2, 4.3, 4.4_

- [x] 4.6 クエリ数が件数に依存しないことを検証するテストを追加する
  - 1 件の一覧と 20 件の一覧で、投稿固有の付随データ（メディア・タグ・絵文字・インタラクション状態・投票）の取得回数が変わらないことを検証する
  - 同一著者の投稿を複数含む一覧で、著者の解決回数が投稿数ではなく著者の種類数に一致することを検証する
  - 完了状態：上記 2 つの検証が通り、逐次処理に戻すと落ちる状態になっている
  - _Requirements: 5.1, 5.2, 5.3_
  - _Depends: 4.5_

- [ ] 5. 複合書き込みを原子化する

- [x] 5.1 書き込みリポジトリ関数を任意のエグゼキュータで実行できるようにする
  - 投稿挿入・メディア添付・カウンタ調整・投票挿入・タグ登録・タグ関連付け・お気に入り追加/削除を、接続プールでもトランザクションでも実行できる形に変える
  - この変換は純粋に追加的であり、接続プールはそのまま渡せるため既存の呼び出し側は変更不要
  - 完了状態：対象関数がトランザクションを渡して呼べるようになっており、既存の呼び出し側を一切変更せずに全テストがグリーン
  - _Requirements: 6.3_
  - _Boundary: StatusRepository, PollRepository, TagRepository, InteractionRepository_

- [x] 5.2 投稿作成を単一トランザクションにまとめる
  - 投稿本体の挿入・メディア添付・投票挿入・タグ登録・親投稿の返信カウント加算を 1 つのトランザクションに入れ、すべて成功した場合のみコミットする
  - **Activity の配送と通知の発行は必ずコミット後**に行う。ネットワーク I/O をトランザクション内に入れると接続を占有し、配送失敗が正常なローカル書き込みを巻き戻す
  - べき等キーの束縛処理の実際の呼び出し位置を確認し、トランザクションに含めるべきかを判断して記録する
  - 完了状態：途中で失敗させたとき、投稿行・メディア関連・投票・タグ・親投稿の返信カウントのいずれも変化していないことを統合テストが示す。成功時のレスポンスとカウンタ値は従来と一致する
  - _Requirements: 1.2, 1.6, 6.1, 6.3, 6.4, 6.5_
  - _Depends: 5.1_
  - _Boundary: StatusService_

- [x] 5.3 ブースト・お気に入り・お気に入り解除を単一トランザクションにまとめる
