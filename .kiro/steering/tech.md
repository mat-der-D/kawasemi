# Technology Stack

## Architecture

単一バックエンドが SPA 配信・API・ActivityPub 連合・非同期タスク処理をすべて担うモノリス構成。外部依存はできる限り抑え、ランタイムは「アプリ + PostgreSQL」のみを目指す。

- **ローカル配送：意味論は対称、物理配送は最適化**。ローカル宛でも Activity の生成・可視性判定・状態遷移はリモートと完全に共通のコードパスを通す。分岐させるのは最終的な配送手段（in-process 関数呼び出し or HTTP 送信）のみ。
- ショートカット（in-process 配送）は JSON-LD シリアライズ／署名往復を通らないため、ローカルでは顕在化せずリモート連合でだけ壊れるバグを生みやすい。論理的に同一の Activity オブジェクトを生成・検証してから配送関数を分岐させる。

## Core Technologies

- **言語（バックエンド）**：Rust（Edition 2024）
- **Web フレームワーク**：axum
- **非同期ランタイム**：tokio
- **DB**：PostgreSQL
- **DB クエリ**：sqlx
- **非同期タスク処理**：DB キュー（外部のジョブブローカーに依存しない）
- **フロントエンド**：TypeScript + React
- **全文検索**：PostgreSQL 内で完結（外部検索エンジン不使用）

## Package Management

- Python を使う補助ツール等では `pip install` ではなく **uv** を使う（`uv venv` / `uv add` / `uv sync`）。

## Development Standards

### Testing — AI 自律 TDD が前提

Mastodon 互換 API は **Opus による自律 TDD**（契約固定 → 実装 → グリーン → レビューの垂直スライス自走）で実装する。コーディングのスループットはボトルネックではなく、**設計判断とレビューが律速**。テストの階層と責務を分ける：

- **単体**：ハンドラ・シリアライザ。
- **契約**：エンティティ（Status / Account / Notification / Poll …）の JSON 形をゴールデン／スナップショットで先に固定し、実装をそれに合わせる。
- **統合**：DB 込みのエンドポイント往復。
- **連合**：自前インスタンスを 2 つ起動して Activity 往復を検証。ローカル最適化パス（in-process）と HTTP 連合パスが**同じ結果**になることを必ずテストする。
- **E2E**：実クライアント（Ivory・Elk・Phanpy）のキャプチャ再生を最終受け入れ基準にする。

### 決定性の強制

時刻・ID・乱数・署名鍵は**注入可能（DI）**にする。clock / id generator / RNG / 署名鍵を差し替え可能な境界に置く。非決定的（flaky）なテストは自律ループを壊す。

### 仕様の出典・優先順位

一次情報は**実装の実挙動**（Mastodon 本体の実レスポンス）。**ドキュメント < 実レスポンス**で扱う。既存クライアントの実リクエストをキャプチャしてフィクスチャ化し受け入れ基準にする。

### 可観測性

失敗時にリクエスト／レスポンス／実行 SQL を十分に出力する。AI が原因特定・自己修正できる診断情報を欠かすとループが停滞・誤修正に陥る。

### 一覧のクエリ数は件数に依存させない

一覧レスポンスの組み立てでは、**必要な素材を件数分ではなく一括で 1 度に解決してから**レンダリングする。クエリ数は「どんな種類の素材があるか」の関数であって「何件返すか」の関数ではない。ブースト先も自分の作者・添付・タグ・絵文字・投票を持つ独立した行なので、同じ一括解決の対象に含める。

- レンダリング段（同期関数）からリポジトリを await できない構造にしておくと、この規約は構造で守られる。await が必要になった時点で件数比例に戻っている。
- 一括化が 1 件ずつの取得と等価であることの根拠（結果集合が同一・順序が同一）は、等価でなくなる変更を防ぐためにコード側に書き残す。
- 一括解決の結果は**1 回の呼び出しの中でのみ**メモ化する。呼び出しをまたいでキャッシュすると、クエリ数と引き換えに「更新前の表現を返す」バグの class を持ち込むことになる。
- 回帰は「クエリ数が件数に依存しないこと」を検証するテストで押さえる（速度ではなく回数を見る）。

### 複合書き込みのトランザクション境界

複数行にまたがる書き込み（投稿作成・ブースト・お気に入り登録／解除など）は 1 トランザクションにまとめ、**全部成功した場合のみ commit** する。途中の `?` による early return が未 commit の `tx` を drop してロールバックする形にしておき、「成功したように見える部分書き込み」を作らない。

**ネットワーク I/O と DB 外の観測可能な副作用（Activity 配送・通知発火）は必ず commit の後に置く。** 送信待ちの間プール接続を保持すると枯渇させるし、配送失敗で正当なローカル書き込みまで巻き戻すことになる。

### ドメイン失敗の識別は型で行う

「この失敗かどうか」で分岐する必要がある呼び出し元は、`AppError` の `public_message` をリテラル比較してはならない（コンパイラが検査できず、メッセージの文言を直した瞬間に静かに外れる）。横断エラー型 `AppError` に `ErrorTag` を持たせ、これで識別する。

- `ErrorTag` は**全ドメインのエラー分類を列挙する場所ではない**。`AppError` は全モジュールが依存する横断型なので、ここに語彙を溜めると全モジュールが互いのエラー分類に依存する。「ある呼び出し元が本当にその失敗を兄弟から区別しなければならない」場合にのみ variant を足す。
- タグはワイヤに出ない（レスポンスレンダラもログも読まない）。タグを付けてもクライアントの観測結果は変わらない。

## Key Technical Decisions

> 本節は**採用予定の技術判断**を含み、実装済みを意味しない。未着手のものは各項に明記する。実装状況の一次情報はコードであり、進行段階は `roadmap.md` を見る。

- **配布形態**：事前ビルド済み（x86_64 / aarch64 Linux）。可能なら musl static 単一バイナリを第一候補とするが、真の要件は「インストールが簡単」であり単一バイナリには固執しない。メディア処理でネイティブ依存（libvips・ffmpeg 等）が要る場合は Docker イメージ等に切り替えてよい。
- **React 資産の埋め込み**（Phase 4 予定・未実装）：ビルド済みフロントをバイナリに埋め込み（`rust-embed` 等）、バックエンドが SPA を配信。Node も別 Web サーバーも不要。
- **DB マイグレーション**：埋め込み + 起動時自動実行（`sqlx migrate`）。up とデータ保持、失敗時の安全停止をテストする。
- **HTTPS**（Phase 4 予定・未実装）：デフォルトは内蔵 ACME（`rustls-acme` 等、Let's Encrypt 自動取得・更新・TLS 終端）。オプションでリバースプロキシ後段（`X-Forwarded-*` 尊重）。
- **設定の二層化**：起動設定（ドメイン・DB 接続・シークレット）は TOML / 環境変数。運用設定（インスタンス情報・トグル等）は DB 保存 + 管理画面編集。
- **検索の抽象化**：検索処理を抽象レイヤーの背後に置き、初期は標準 PostgreSQL の最小実装。`pg_bigm` 等の日本語拡張は任意オプションに留め、必須にしない。API 契約は Mastodon 検索 API の形に留める。
- **横断サブシステム**：OAuth 2.0 サーバー・ページネーション規約（`Link` + `max_id`/`since_id`/`min_id`）・エラー/レート制限互換（`X-RateLimit-*`）・非同期メディアアップロード（`202` → ポーリング）は Phase 1 で実装済み。Streaming API（WebSocket）・Web Push（VAPID）は **Phase 2 予定・未実装**（`roadmap.md` 参照）。

## テスト実行基盤の既知事項

テスト実行基盤（アプリ本体のロジックではない）について、コードから読み取れない事情。
フィクスチャの構造・隔離・回収そのものは `structure.md`「テストレイアウト」に記載する。

- **RSA-2048 鍵生成が debug ビルドで低速**：1 鍵あたり約 10.8 秒かかっていた。`Cargo.toml` の `[profile.dev.package.*]` で `rsa` 等の関連クレートに `opt-level = 3` をオーバーライドして解消済み（約 22 倍高速化、テストスイート全体で約 2.4〜3 倍高速化）。**このオーバーライドを外すとテストスイートが数倍遅くなる。**
- **`cargo test --lib` は単一プロセスで完走する。** かつては 256 件が `PoolTimedOut` で落ち、モジュール分割と事前のスキーマ掃除を手順書として踏む必要があったが、いずれも不要になった。真因は `Drop for TestApp` が `pool.close()` を呼んでいなかったこと（スキーマ削除のデタッチはしていたので「スキーマは消えるが接続は残る」状態だった）。回収機構は `structure.md`「隔離とその回収」を参照。
- **`cargo build --tests` と `--all-features` は `target/debug/libkawasemi.rlib` を feature ON 版で上書きする。** 成果物の中身（テスト専用資産が入っていないこと等）を検査するときは、直前に必ず素の `cargo build` / `cargo build --release` を打つこと。さもないと偽の失敗を見る。
- **共有テスト DB の状態を測るテストはテスト間分離を自前で持つこと。** `information_schema` や `pg_stat_activity` をサーバ全体で舐めると、兄弟テストの生存スキーマ・接続を自分の残骸と誤検出して flaky になる。観測対象は自分が作った名前に限定し（`= ANY($1)`）、必要なら排他ロックを取る。
- **`bootstrap_lifecycle_it` が `public` スキーマの不整合で恒久的に失敗する事象**：並行実行していた別プロセスが `public` スキーマの `_sqlx_migrations` に、実体を伴わないバージョンの履歴行を残し、以後そのスキーマに対するマイグレーション適用が失敗し続けていた。該当テーブルと履歴行を直接 `DROP` して解消（コード修正ではなく DB 状態のクリーンアップ）。同様の中断（複数プロセスが同一スキーマへ同時にマイグレーションを試みる等）が起きると再発し得る。
- **`federation::outbound::worker` のクレーム件数 0（原因特定済み・テスト固有・未修正）**：`run_once_marks_a_job_failed_immediately_when_sender_no_longer_resolves` が `summary.claimed == 0` で落ちることがある。原因は `spawn_test_app` が `federation_background.spawn()` により**本物の配送ワーカーのループを同じプール・同じスキーマ上で常時走らせている**ことで、テスト自身の `run_once` より先にそのループが同じジョブをクレームするため。`claim_due` の `FOR UPDATE SKIP LOCKED` は仕様どおりに動作しており、ジョブは正しく一度だけ処理される（失われる仕事はない）。プロダクションでは `claim_due` の呼び出し元は配送ループ 1 つだけなので、この競合は起きない — **プロダクションの欠陥ではない**。プールサイズは原因ではなく競合の窓を広げる増幅器で、プール 1 では決定的に失敗、現行のプール 2 では低頻度で再現する（独立した 2 回の計測で 34 回中 1 回・40 回中 1 回。単体実行でも起きるのでフル並列限定ではない）。**この 1 件が落ちても資源枯渇ではない。**
