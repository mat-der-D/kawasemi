# Technology Stack

## Architecture

単一バックエンドが SPA 配信・API・ActivityPub 連合・非同期タスク処理をすべて担うモノリス構成。外部依存はできる限り抑え、ランタイムは「アプリ + PostgreSQL」のみを目指す。

- **ローカル配送：意味論は対称、物理配送は最適化**。ローカル宛でも Activity の生成・可視性判定・状態遷移はリモートと完全に共通のコードパスを通す。分岐させるのは最終的な配送手段（in-process 関数呼び出し or HTTP 送信）のみ。
- ショートカット（in-process 配送）は JSON-LD シリアライズ／署名往復を通らないため、ローカルでは顕在化せずリモート連合でだけ壊れるバグを生みやすい。論理的に同一の Activity オブジェクトを生成・検証してから配送関数を分岐させる。

## Core Technologies

- **言語（バックエンド）**：Rust（Edition 2024）
- **Web フレームワーク**：axum
- **非同期ランタイム**：tokio
- **DB**：PostgreSQL
- **DB クエリ**：sqlx
- **非同期タスク処理**：DB キュー（外部のジョブブローカーに依存しない）
- **フロントエンド**：TypeScript + React
- **全文検索**：PostgreSQL 内で完結（外部検索エンジン不使用）

## Package Management

- Python を使う補助ツール等では `pip install` ではなく **uv** を使う（`uv venv` / `uv add` / `uv sync`）。

## Development Standards

### Testing — AI 自律 TDD が前提

Mastodon 互換 API は **Opus による自律 TDD**（契約固定 → 実装 → グリーン → レビューの垂直スライス自走）で実装する。コーディングのスループットはボトルネックではなく、**設計判断とレビューが律速**。テストの階層と責務を分ける：

- **単体**：ハンドラ・シリアライザ。
- **契約**：エンティティ（Status / Account / Notification / Poll …）の JSON 形をゴールデン／スナップショットで先に固定し、実装をそれに合わせる。
- **統合**：DB 込みのエンドポイント往復。
- **連合**：自前インスタンスを 2 つ起動して Activity 往復を検証。ローカル最適化パス（in-process）と HTTP 連合パスが**同じ結果**になることを必ずテストする。
- **E2E**：実クライアント（Ivory・Elk・Phanpy）のキャプチャ再生を最終受け入れ基準にする。

### 決定性の強制

時刻・ID・乱数・署名鍵は**注入可能（DI）**にする。clock / id generator / RNG / 署名鍵を差し替え可能な境界に置く。非決定的（flaky）なテストは自律ループを壊す。

### 仕様の出典・優先順位

一次情報は**実装の実挙動**（Mastodon 本体の実レスポンス）。**ドキュメント < 実レスポンス**で扱う。既存クライアントの実リクエストをキャプチャしてフィクスチャ化し受け入れ基準にする。

### 可観測性

失敗時にリクエスト／レスポンス／実行 SQL を十分に出力する。AI が原因特定・自己修正できる診断情報を欠かすとループが停滞・誤修正に陥る。

## Key Technical Decisions

> 本節は**採用予定の技術判断**を含み、実装済みを意味しない。未着手のものは各項に明記する。実装状況の一次情報はコードであり、進行段階は `roadmap.md` を見る。

- **配布形態**：事前ビルド済み（x86_64 / aarch64 Linux）。可能なら musl static 単一バイナリを第一候補とするが、真の要件は「インストールが簡単」であり単一バイナリには固執しない。メディア処理でネイティブ依存（libvips・ffmpeg 等）が要る場合は Docker イメージ等に切り替えてよい。
- **React 資産の埋め込み**（Phase 4 予定・未実装）：ビルド済みフロントをバイナリに埋め込み（`rust-embed` 等）、バックエンドが SPA を配信。Node も別 Web サーバーも不要。
- **DB マイグレーション**：埋め込み + 起動時自動実行（`sqlx migrate`）。up とデータ保持、失敗時の安全停止をテストする。
- **HTTPS**（Phase 4 予定・未実装）：デフォルトは内蔵 ACME（`rustls-acme` 等、Let's Encrypt 自動取得・更新・TLS 終端）。オプションでリバースプロキシ後段（`X-Forwarded-*` 尊重）。
- **設定の二層化**：起動設定（ドメイン・DB 接続・シークレット）は TOML / 環境変数。運用設定（インスタンス情報・トグル等）は DB 保存 + 管理画面編集。
- **検索の抽象化**：検索処理を抽象レイヤーの背後に置き、初期は標準 PostgreSQL の最小実装。`pg_bigm` 等の日本語拡張は任意オプションに留め、必須にしない。API 契約は Mastodon 検索 API の形に留める。
- **横断サブシステム**：OAuth 2.0 サーバー・ページネーション規約（`Link` + `max_id`/`since_id`/`min_id`）・エラー/レート制限互換（`X-RateLimit-*`）・非同期メディアアップロード（`202` → ポーリング）は Phase 1 で実装済み。Streaming API（WebSocket）・Web Push（VAPID）は **Phase 2 予定・未実装**（`roadmap.md` 参照）。

## テスト実行基盤の既知の問題

フル並列でのテストスイート実行（`cargo test --lib` 等）を調査した際に見つかった、テスト実行基盤（アプリ本体のロジックではない）に関する既知事項。

- **RSA-2048 鍵生成が debug ビルドで低速**：1 鍵あたり約 10.8 秒かかっていた。`Cargo.toml` の `[profile.dev.package.*]` で `rsa` 等の関連クレートに `opt-level = 3` をオーバーライドして解消済み（約 22 倍高速化、テストスイート全体で約 2.4〜3 倍高速化）。
- **`TestApp::cleanup()` 未実行時の孤立スキーマ**：`src/test_harness.rs` の `Drop for TestApp` は、パニックやプロセス終了時に teardown の detached task が完了しないと、コメント上で言及されている「将来の起動時スイープ」が実装されていないため `kawasemi_test` DB 内に `test_*` スキーマが溜まり続ける（今回 664 件を検出し手動 `DROP SCHEMA` で解消）。恒久対応には、起動時または CI 前処理での孤立スキーマ一括回収スイープの実装が必要（未着手）。
- **`bootstrap_lifecycle_it` が `public` スキーマの不整合で恒久的に失敗する事象**：並行実行していた別プロセスが `public` スキーマの `_sqlx_migrations` に、実体を伴わないバージョン（8）の履歴行を残し、以後そのスキーマに対するマイグレーション適用が失敗し続けていた。該当テーブルと履歴行を直接 `DROP` して解消（コード修正ではなく DB 状態のクリーンアップ）。同様の中断（複数プロセスが同一スキーマへ同時にマイグレーションを試みる等）が起きると再発し得る。
- **`federation::outbound::worker` の間欠的失敗**：フル並列テスト実行時にごく稀に、`claim_due`（`UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING ...` という単一アトミック文）のクレーム件数が 0 になることがある。SQL 自体のロック戦略は正しく、`federation::` 単体やモジュール単位の再実行では再現しない。CPU / Postgres カタログ競合など、フル並列実行時の環境要因による flake と推測されるが、決定的な再現手順は未特定。既知の flake として監視対象にとどめる。
